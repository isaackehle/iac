# Outage: Portainer unreachable — 2026-08-02/03

Portainer was unreachable for roughly eight hours. Several real problems were
found and fixed along the way, but none of them were the reason the site was
down. The actual cause was corrupted `tailscaled` path state in the
`portainer-tailscale` container.

## Root cause

`portainer-tailscale`'s persisted state in `ts-state/` held a bad MTU / path-discovery
value. Small responses went through; anything larger vanished. TCP always
connected and the request was always accepted — nothing came back.

This is why it took so long: the failure was **payload-size dependent**, so it
presented differently depending on what was being tested, and every test looked
like evidence for a different theory.

| Test                                        | Result             |
| ------------------------------------------- | ------------------ |
| `GET /api/status` (72-byte JSON)            | 200, instant       |
| `GET /` (full HTML UI)                      | hang, then timeout |
| `https://portainer.<tailnet>.ts.net`        | hang at TLS Client Hello |
| `http://<tailscale-ip>:9000` ("direct" IP)  | hang — not a bypass |
| `tailscale ping` (default size)             | pong, 25ms         |
| `tailscale ping --size 1300`                | timeout            |

The decisive test was comparing against a healthy sidecar on the same host,
to the same peer, over the same DERP relay:

```shell
docker exec portainer-tailscale tailscale ping --size 1300 discovery   # timed out
docker exec pihole-tailscale    tailscale ping --size 1300 discovery   # pong, 27ms
```

Same NAS, same peer, same relay — only `portainer-tailscale` failed. That isolated the
fault to that one node's local state. Because `tailscaled` persists this state
on disk, no amount of restarting, recreating containers, or fixing configs would
ever have cleared it.

### Fix

```shell
cd /volume1/docker/stacks/portainer
docker compose down
rm -rf ts-state/*
docker compose up -d
```

The node re-registered clean, took a new tailnet IP (`100.94.37.89` →
`100.113.2.94`, hostname unchanged), re-issued its Let's Encrypt cert
automatically after ~2 minutes, and `--size 1300` pings then succeeded both
ways. `https://portainer.tail303fda.ts.net` returned 200.

## Also fixed along the way

Real problems, all genuinely broken, none of them the outage:

- **Port 19443 conflict** — stale host-level `tailscale serve` mapping. Cleared
  with `tailscale serve reset`, which also wiped the affine/frigate/postgresql
  mappings (reapply via `scripts/serve-all.sh`).
- **No `portainer` service in the compose file** — only the sidecar was defined.
- **`hostname: portainer` on the sidecar** — caused a DNS collision; removed.
- **Orphaned Docker network** from a Compose project rename — Compose prefixes
  network names with the project name, so `portainer_net` was really
  `portainer-ts_portainer_net`, and the stale one blocked redeploys with
  "network is busy".
- **Split data paths** — live data in `/volume1/docker/portainer/`, new standard
  path `/volume1/docker/stacks/portainer/`. Migrated with copy-then-verify.
- **Repo dumped into Portainer's `/data` volume**, including a real
  `iac-secrets.env`. A live Tailscale auth key was also found in plaintext in
  `synology-mcp/PORTAINER-DEPLOYMENT.md`. **Both still need rotating.**
- **Broken serve proxy target** — `https+insecure://portainer:9443`, a bare
  hostname that cannot resolve under `network_mode: service:`, since there's no
  independent network attachment.
- **Compose file missing from the canonical path** — the file actually in use
  was a stray nested copy at `data/portainer/docker-compose.yml`, inside
  Portainer's own data volume.
- **Stale namespace** from restarting the sidecar alone (see DEBUG.md trap #1).
- **Empty database** — `portainer.db` had no admin account and wasn't
  recoverable; a fresh admin was created.

## Architecture change

Portainer now uses the same Caddy sidecar pattern as Pi-hole. `serve.json` does
`TCPForward` + `TerminateTLS` to Caddy on `:8444`; Caddy reverse-proxies to
Portainer's plain HTTP `:9000`. This replaces tailscaled's built-in `Web`/`Proxy`
serve mode, which is documented as 5-10x slower under load
([tailscale/tailscale#18307](https://github.com/tailscale/tailscale/issues/18307)).

This was originally deployed as *the* fix, based on the theory that the proxy
bug explained the hang. It didn't — the hang persisted afterward, and was only
resolved by the state wipe. The change is kept because it's the correct pattern
and matches the rest of the repo, but it should not be remembered as the fix.

## What went wrong in the diagnosis

Worth keeping, because these are repeatable mistakes:

- **Testing `.ts.net` from the NAS's own shell.** Voyager resolves those names
  via public DNS, not Tailscale's resolver, so `curl` returned an unrelated
  Fastmail page that was read as a real response. An entire theory was built on
  it. `nslookup` would have caught this immediately.
- **Declaring a fallback "confirmed working" from stale evidence.** The
  `http://<ip>:9000` direct-IP path was reported working based on an earlier
  test against a *different port and protocol*, run before the failure appeared.
  It had never worked. It went through the same broken node.
- **Guessing from file size.** The larger `portainer.db` was assumed to be the
  real one; BoltDB pre-allocates ~256KB regardless of content, so size said
  nothing. Both were empty.
- **Not isolating early.** The single most informative test — comparing
  `--size 1300` against a known-good sidecar on the same host — took two minutes
  and could have been run in the first hour. Where a working peer exists,
  compare against it before theorizing.
